## 修复：JSONPath 求值器三处致命 bug（此前该功能完全不可用）
- **现象**：`pm.response.jsonPath('$.data.access_token')` 等任意多层路径都取不到值（返回空数组），连 `$.code` 都不行。之前一直无人实测多层路径，故未发现。
- **根因（同文件 `InterfaceManagement.vue` 顶部 `tokenizeJsonPath` / `jsonPathQuery` / `evalJsonPathFilter`）**：
  1. **词法吞掉首个 key 段**：`tokenizeJsonPath` 在 `$` 后 `if (path[i] === '.') i++` 跳到首个 key 的首字母，但 while 循环对非 `.`/`[` 字符只 `i++`，从不把该 key 加入 token；且 `$..` 的第二个 `.` 也被这个跳点误判 → 首个路径段（如 `data`）被丢弃。
  2. **`root` 分支清空 nodes**：`jsonPathQuery` 循环每轮 `const next = []`，`case 'root'` 仅 `break` → 随后 `nodes = next` 把数据清空成 `[]`，第一步即丢光。
  3. **过滤器 `@` 非法标识符**：`evalJsonPathFilter` 用 `new Function('@', ...)`，但 `@` 在 JS 中不是合法参数名 → 抛错被 catch 吞掉，过滤器永远 false。
- **修复**：
  1. 移除 root 块多余的点号跳点，让 `$.`/`$..` 统一由 `.` 分支处理；并在兜底分支增加"裸标识符匹配"（`/^([a-zA-Z_$][\w$]*)/`），识别紧接 `$`/`..` 之后的 key。
  2. `case 'root'` 改为 `next.push(...nodes)`。
  3. 过滤器改用合法参数名 `_it`，并对表达式做 `expr.replace(/@/g, '_it')`。
- **验证**：用 Node 临时脚本对真实响应跑了 13 个用例，覆盖 `$.data.access_token`、`$.code`、`$..access_token`、`$.list[0].id`、`$.list[*].id`、`$.list[1:3]`、`$.list[-1]`、`$.list[?(@.role=='admin')].id`、`$..id` 等，全部正确。已删除临时脚本。`npm run build` 通过（3 个 ERROR 为既有 RequestModel/editCollection，无关）。
- **要点**：`jsonPath` 返回**数组**（与 Postman 一致），取单个值加 `[0]`；不加 `[0]` 也能用，因为 `pm.environment.set` 内部会 `String(value)` 把单元素数组转成字符串。

## 修复：cURL 导入后 body 错误进入 json 模式（加密报文场景）
- **现象**：导入带 `content-type: application/json` + `--data-raw "加密长字符串"`（如 `isencrypt: true` 的登录请求）的 curl 后，body 被解析为 json 模式，UI 显示异常、发送时被 `JSON.stringify` 给字符串加引号导致请求错误。
- **根因**：`parseCurl()` 仅按 Content-Type 判定 body 模式（json → json），未校验 body 是否真的是合法 JSON。加密/普通文本被错误标记。
- **修复**：新增 `isValidJson()` 辅助函数。`content-type=application/json` 时**仅当 body 是合法 JSON 才用 json 模式，否则回退 raw**；真实 JSON 报文仍走 json 模式，不影响。
- **顺带修复 `toCurl()` 导出丢 body**：原 `toCurl()` 只处理 `raw` 模式，json/urlencoded/formdata 的 body 在导出时被完全丢弃。已补齐四种模式的导出（json 自动 stringify、urlencoded 拼 key=val、formdata 用 `-F`）。

## 修复：cURL 含 JSON body（内部带引号）时分词器切碎 body
- **现象**：导入形如 `--data-raw "{...真实JSON...}"` 的 curl（body 是合法 JSON）时，body 数据错乱/不完整，不是期望的完整 JSON。
- **根因**：原 `tokenizeCurl()` 用正则 `"([^"]*)"` 分词。当 body 内部含大量 `"`（JSON 必有）时，正则会在每个内部 `"` 处把 JSON 切断，只取到第一个 `{`，其余片段被误判为奇怪的 token/URL → bodyText 残缺。
- **补充背景**：用户粘贴的是 **Windows cmd 风格 curl**——行继续符为 `^`（如 `curl ... ^`），且 JSON 内的 `"` 与 `{`/`}`/`[`/`]` 等特殊字符被 cmd 转义为 `^"`、`\^"`、`\^X` 等形式。原预处理只去除了 bash 的 `\` 续行，未处理 cmd 的 `^`。
- **修复**：将 `tokenizeCurl()` 替换为**类 shell 状态机分词器**：
  - 新增 `normalizeCurl()`：去除 cmd 行继续符 `^\s*\n` 与 bash 续行 `\s+`；
  - 正确区分单引号 `'(...)'` 与双引号 `"(...)"` 整体；
  - 双引号内处理 `\^X` → `X`（cmd 转义，`X` 为任意特殊字符）、`\"` → `"`、`^X` → `X`（含 `^"`）；引号外 `^`/`\` 同样作为转义符。
  - 配合上一轮的 `isValidJson()`：`content-type=json` 且 body 为合法 JSON → json 模式（导入时映射为 raw 编辑器 + json 类型，即用户期望的"body 选 raw 且数据正确"）；加密/非 JSON 文本 → raw。
- **验证**：Node 脚本对 4 类用例测试通过——① cmd 风格合法 JSON 数组对象（`wrongQuestionTypes`）② DevTools 单引号风格 JSON ③ 加密 body（无内部引号）④ 嵌套对象数组。均解析为合法 JSON / 正确 raw。
- **涉及文件**：`frontend/src/utils/requestModel.ts`（已重新 `npm run build`）
- **数据流向确认**：`InterfaceManagement.vue` 导入逻辑 `requestModel.body.mode==='json'` 时设 `bodyType='raw', rawType='json', rawBody=body.json`；发送时 `JSON.parse(rawBody.value)`。故 body.json 存字符串与现有流程一致，无需改 vue。

## 追加修复：聊天粘贴的 `^\^X` 双重转义导致 JSON 内引号残留反斜杠
- **现象**：用户再次粘贴同一 cmd 风格 JSON curl，解析后 body 变成 `{\"pageNum\":1,...}`（带反斜杠的非法 JSON，`isValidJson=false`）。
- **根因**：聊天渲染把 cmd 转义 `"` 显示成 `^\^"`（caret-backslash-caret-quote）这种**双重转义**序列。原分词器只处理 `\^X`，遇到 `^\^X` 时 `^X->X` 把 `\` 保留了下来，于是 `^\^"` → `\"`（多一个反斜杠）。
- **修复**：在 `tokenizeCurl()` 双引号状态中，于 `\^X` 规则**之前**新增一条 `^\^X -> X`（`c==='^' && next==='\\' && next2==='^'` 时取 `cmd[i+3]` 并跳过 4 个字符）。该规则与既有 `\^X`、`^X`、`\"` 规则互不冲突（触发条件不同），不影响其他转义形式。
- **验证**：用用户真实 curl 文本（String.raw 精确保留反斜杠）跑解析，输出 `bodyText === expected` 为 `true`、`isValidJson=true`，格式化后即为完整正确 JSON。`npm run build` 通过。
- **结论**：该 curl 完整解析链路为 `normalizeCurl`（去 `^`续行/ `\`续行）→ `tokenizeCurl`（shell 状态机分词 + `^\^X`/`\^X`/`^X`/`\"` 多种转义还原）→ 取 `--data-raw` 文本 → `content-type=json` 且 `isValidJson` 为真 → body 设为 json 模式 → 前端映射为 raw 编辑器 + json 类型。

## Bug 修复：导入 curl 与导出 curl 结果不一致（请求体丢失）
- **现象**：用户导入一个带 JSON body 的 curl 后，点「导出为 CURL」得到的 curl 完全没有请求体，与原 curl 是「两个不同请求」。
- **根因**：`InterfaceManagement.vue` 的 `exportRequest()` 在组装 `requestModel` 时，把 `body` 硬编码为 `{ mode: 'none', raw: rawBody.value || '' }`。而 `RequestModelParser.toCurl()` 对 `mode === 'none'` 不输出任何 `-d` 参数，导致 body 被整段丢弃。
- **修复**：改为根据当前 UI 的 Body 状态（`bodyType`/`rawType`/`rawBody`/`formData`/`formUrlEncoded`）推导 body 模式：
  - `raw`+`json` → `{ mode:'json', json: rawBody }`；`raw`+非 json → `{ mode:'raw', raw: rawBody }`
  - `form-data` → `{ mode:'formdata', formdata: formData }`；`x-www-form-urlencoded` → `{ mode:'urlencoded', urlencoded: formUrlEncoded }`；`binary` → `{ mode:'binary' }`；否则 `none`。
  - 仅当对应内容非空时才设置具体模式，空内容回退为 `none`（不输出 body）。
- **另一条导出路径（代码生成下拉的 cURL / `generateCode('curl')`）**：其 `requestModel.body` 已同时正确填 `raw`/`json`/`formdata`/`urlencoded`，`codeGenerator.buildCurlBody` 能正确处理，无需改。
- **注意**：`InterfaceManagement.vue` 的 `<script setup>` 是**纯 JS**（无 `lang="ts"`），不可写 `: any` 类型注解，否则 vite build 报 "Missing semicolon"。已用 `let exportBody = {...}` 规避。
- **验证**：`npm run build` 通过。导入→（UI 状态）→导出形成闭环，body 不再丢失，往返语义一致。
- **结论**：导入解析用 `RequestModelParser.parseCurl`（normalize→tokenize→取 --data-raw→按 content-type 判定 mode），导出用 `RequestModelParser.toCurl`；两者通过 UI 的 `bodyType/rawType/rawBody` 等状态桥接，现已互逆一致。

- **真正根因**：第一次只给 `.node-label` 加了 `min-width:0` + ellipsis，但漏了 `.tree-node` 本身。`.tree-node` 是 el-tree 节点内容容器 `.el-tree-node__content`（display:flex）的子项，带 `flex:1` 却仍是 `min-width:auto`，因此长名称会把整个 `.tree-node` 撑开到内容宽度、超出侧边栏可视区，方法标签被推到可视区外（被 sidebar 的 overflow 裁切），看起来「没固定显示」。

- **验证**：`npm run build` 通过。
- **排查要点**：el-tree 自定义节点长文本挤压类问题，三层都要限制 `min-width:0`：① 自定义 wrapper（`.tree-node`）② 被 wrapper 内的文本元素（`.node-label`）③ el-tree 内部内容容器（`.el-tree-node__content`，需 `:deep`）。仅改其中一层往往不够。

## 新功能：Tests（请求后脚本）提取响应并写回环境变量
- **需求**：接口管理页"Tests"脚本（字段 `post_request_script`）应能提取响应数据，并保存/替换当前项目的环境变量，使后续接口通过 `{{变量名}}` 复用（类似 Postman 的 `pm.environment.set`）。
- **根因/现状**：后端 `execute` 视图（`apps/api_testing/views.py` ~L409）只做变量替换+发送+断言，**从不执行** `post_request_script`/`pre_request_script`（脚本此前仅存储、从未运行）。变量替换语法为 `{{name}}`，读取 `Environment.variables`（JSONField，`{'key': {'initialValue':'','currentValue':''}}` 形状，后端 `_replace_variables` 优先读 `currentValue`）。
- **方案（前端执行，与 Postman 一致）**：请求后端返回响应后，在 `sendRequest` 中 `await runPostRequestScript(apiResponse.data)` 于前端用 `new Function('pm','console', script)` 执行脚本。

## 新功能：Tests（请求后脚本）在「自动化测试 / 定时任务」服务端执行
- **诉求**：Tests 脚本此前只在「手动单接口调试」时于前端执行；**自动化测试（测试套件）与定时任务走后端 `execute` 根本不执行脚本**，导致 `pm.environment.set` 等失效、变量无法串联。
- **方案**：服务端用 **Node 子进程**执行同一套 JS 脚本（脚本是 JS 语法，必须用 JS 引擎），与前端 `pm` API 完全镜像，保证行为一致。
- **新增文件**：
  - `apps/api_testing/tests_runner.js`：Node 脚本，从 stdin 读 `{script, response, environments}`，镜像前端 `tokenizeJsonPath/jsonPathQuery/collectDescendants/evalJsonPathFilter` + `pm.{response,environment,globals,test,expect,jsonPath}` + `console.{log,warn,error}`，回写 `{testResults,scriptLogs,savedEnvVariables,updatedEnvironments,error}` 到 stdout。`environment.set` 把变量写成 `{initialValue,currentValue}`；`updatedEnvironments` 仅含被改动的 env。
  - `apps/api_testing/js_runner.py`：`run_tests_script(script, response_info, environments)`，用 `subprocess.run([node, tests_runner.js], stdin=JSON, timeout=30)`；`shutil.which('node')` 找不到 node 时返回降级错误结果（不中断请求）。**依赖服务器安装 Node.js**（与前端构建同 node）。
  - `apps/api_testing/utils.py`：新增 `run_post_request_script(api_request, response, response_time, environment)`，构建 `response_info` 与 `environments`（当前环境 current:true + 项目级 GLOBAL 环境），调用 runner，并**持久化** `updatedEnvironments` 到 `Environment` 表（同时更新内存 `environment.variables` 以支持套件内请求间变量串联）。
- **接入点（四处，均把 `tests_result` 写入 `RequestHistory.response_data` 与返回/结果 `results` 数组）**：
  1. `utils.execute_test_suite`（手动 + 定时任务 TEST_SUITE）
  2. `utils.execute_api_request`（定时任务 API_REQUEST）
  3. `views.TestSuiteViewSet.execute`（前端"运行测试套件"按钮）
  4. `views.ApiRequestViewSet.execute`（单次请求端点；手动单接口现在服务端也会存一份 tests_result 到历史，前端仍保留前端执行+PATCH 双写，幂等无害）
- **前端展示**：
  - `RequestHistory.vue` 详情对话框新增「Tests 结果」标签页（`v-if` 有 `response_data.tests_result`），展示断言 PASS/FAIL、已写入环境变量、脚本输出、脚本错误。
  - `AutomationTesting.vue` 执行结果表格新增可展开行，按请求展示 `tests_result`。
  - i18n：`automation.noTests`（中/英）"该请求未配置或无 Tests 脚本执行内容"。
- **验证**：① Node 自测用用户真实 token 响应跑通（`$.data.access_token`→`Bearer ...` 正确写入 env、`pm.test` 断言 PASS、`updatedEnvironments` 正确回传）；② `python -m py_compile` 三个 py 文件 OK；③ `npm run build` 通过（告警均为既有 web-tree-sitter/eval/分片，无关）。
- **要点**：脚本在服务端执行后写入的环境变量会持久化到 DB，套件中后续请求通过 `{{变量}}` 可立即复用；响应 JSON 解析以 `content-type` 含 `application/json` 为准，否则 `pm.response.json()` 回退 `JSON.parse(body)`。

## 优化：报警（定时任务）邮件改为精美 HTML，并展示错误+断言失败+响应实体
- **现象**：定时任务失败时收到的报警邮件是纯文本，丑且**不显示断言失败的响应实体**（只看得到错误与断言期望/实际，看不到实际返回的响应体）。
- **根因**：`apps/api_testing/views.py` 的 `_send_email_notification` 用纯文本 `message` 拼接；而 `execute_test_suite` 的结果项里**失败请求没有携带响应体**（`response.text`），邮件无从展示。
- **改动**：
  1. `apps/api_testing/utils.py` `execute_test_suite` 结果项新增 `response_body: response.text if not passed else None`（仅失败请求携带，控制存储体积）。`API_REQUEST` 任务的结果本身含 `response_data.body`，邮件构建时直接取用。
  2. `apps/api_testing/views.py` `_send_email_notification` 重写：生成**双版本**——`plain_text`（存入 `NotificationLog.notification_content`，供通知日志/详情查看）与 `html_content`（精美 HTML：表头按成败变色、信息卡、通过/失败统计徽章、错误高亮块、每个失败请求一张卡片含 URL/状态码/响应时间/错误 + **断言失败明细表（名称/期望/实际/错误）+ 响应实体 `<pre>` 暗色代码块**）。发送时自定义 SMTP 分支用 `EmailMessage(content_subtype='html')`，默认分支用 `send_mail(html_message=...)`。响应体与所有用户内容均 `html.escape`，JSON 响应体自动 `json.dumps(indent=2)` 美化。兼容 `TEST_SUITE`（results 数组）与 `API_REQUEST`（单结果）两种结构。
  3. 前端 `frontend/src/views/api-testing/NotificationManagement.vue` 通知详情对话框：加宽至 760px，错误信息独立为红色 `el-alert`，内容区改为暗色 `<pre>` 代码块并限制高度滚动。
- **注意**：报警邮件内容由 `execution_log.result` 驱动；失败请求的响应体已随 `execution.results` 持久化，无需改 `RequestHistory`。`response_body` 仅失败项有值，前端自动化执行结果展示不受影响（仍读 `tests_result`）。
- **验证**：`python -m py_compile` 通过；`npm run build` 通过（告警均为既有 web-tree-sitter/eval/分片，无关）；HTML 邮件逻辑独立自检通过（转义、状态码、响应时间均正确）。
- **生效**：重启 Django 后端与 Celery worker。

## 优化（续）：报警邮件断言明细增强 + 去重 + 响应概览
- **用户反馈**：① 邮件仍不显示响应体（实际 `response_body` 上轮已写入，本轮确认仍在）；② 失败断言出现两个同名"断言1"重复；③ 断言应显示"断言状态码/json + 具体断言依据（如 `$.code`）"。
- **根因**：
  - 重复"断言1"：套件执行时 `assertions_results = execute_assertions(...请求断言) + suite_assertions_results`（套件级断言合并），若请求与套件都配了同名同值断言即重复出现。
  - 断言结果无"依据"字段：`execute_assertions` 的结果只含 `name/type/expected/actual/error`，没有 `json_path`/`header_name`，邮件无法展示 `$.code` 这类具体依据。
- **改动**：
  1. `utils.py` `execute_assertions` 的结果字典新增 `json_path`、`header_name` 字段（从断言配置带入），供邮件/报告展示具体断言依据。
  2. `views.py` `_send_email_notification` 新增三个辅助函数：
     - `assertion_type_label`：把 `status_code/json_path/header/...` 映射为中文类型标签；
     - `assertion_basis`：返回断言依据描述——`json_path`→`$.code` 表达式、`header`→响应头名、`status_code`→"响应状态码"、`response_time`→"响应时间 ≤ Xms" 等；
     - `dedup_assertions`：按 (name,type,expected,actual,error) 去重，消除套件/请求级合并导致的完全重复断言。
  3. 邮件 HTML 与明文均改造：断言明细表新增**类型、断言依据**两列；每个失败请求卡片新增**响应概览**块（实际状态码 ｜ 响应时间 + 响应实体 JSON 暗色代码块，自动美化缩进）。
- **验证**：`python -m py_compile` 通过；独立脚本模拟（含 2 个重复 status_code 断言 + 1 个 json_path 断言）确认去重后 3→2、表格含 `$.code` 依据、响应概览与 JSON 正常。
- **注意**：去重只针对邮件展示层，不改动持久化的 `execution.results` 数据。
- **生效**：重启 Django 后端与 Celery worker；响应体需下一次失败执行才会写入并随邮件展示。
