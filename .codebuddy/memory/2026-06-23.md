## 修复：Airtest Minicap 失败自动降级到 ADB 截图

### 问题
设备 `XWSF452620250003` 的 ROM 不支持 Minicap 的 `mv` 命令操作，导致 `init_device()` 阶段报错：
```
b"mv: bad '/data/local/tmp/minicap': Invalid argument"
Minicap setup up failed!
```
清理 `/data/local/tmp/minicap` 残留文件无效，因为问题本质是 ROM 不支持该操作，而非残留文件问题。

### 修复内容 (airtest_base.py) - 第二轮修复
1. **`_verify_screen_health`** (新方法): `init_device()` 成功后调用 `G.DEVICE.display_info` 验证屏幕代理。Minicap 失败时 Airtest 1.4.3 不抛异常，仅记录 ERROR，导致设备"连接成功"但屏幕代理断裂。此检查将静默失败转为显式异常，触发降级流程。
2. **`_safe_disconnect`** (新方法): 断开设备并清空 `G.DEVICE_LIST`，确保 Minicap 失败后 ADBCAP 降级获得干净状态。
3. **`setup_airtest`**: Minicap 重试间加入 `_safe_disconnect()`，最终失败后降级到 `_try_adbcap_fallback()`
4. **`_try_adbcap_fallback`**: 每次 ADBCAP 重试前也调用 `_safe_disconnect()`

### 降级流程（完整）
Minicap → `init_device()` "成功"但屏幕代理断开 → `_verify_screen_health()` 检测失败 → 抛 RuntimeError → `_safe_disconnect()` → 重试3次 → 全部失败 → 降级 ADBCAP → `_safe_disconnect()` → `connect_device(cap_method='ADBCAP')` → `_verify_screen_health()` 通过 → 成功

### 第三轮：发现 NameError bug
详细日志显示 Minicap 降级代码正常工作（屏幕健康检查通过），但测试失败的真正原因是 `test_execute_ui_flow` 函数缺少 `device_id` 参数：
```

```
修复：在函数签名中添加 `device_id` 参数（`conftest.py` 中已定义该 fixture）。
Minicap 错误仅出现在 teardown 阶段（`G.DEVICE.disconnect()` 触发），属于次要问题，Airtest 内部 fallback 到 javacap 处理。

### 第五轮：性能优化 - 单次点击从 27s → 预计 ~10s

用户反馈单元素点击执行耗时 27 秒效率太低。分析日志后分解：

| 阶段 | 耗时 | 说明 |
|------|------|------|
| Minicap 安装+失败+回退 | ~3s | 每次先尝试 Minicap → 失败 → Airtest 内部回退 javacap |
| pytest 启动+设备信息采集 | ~5s | RotationWatcher, dumpsys 等初始化 |

- **原因**: 该设备 (Android 13) 上 Minicap 安装每次都失败（`mv: bad '/data/local/tmp/minicap': Invalid argument`），Airtest 内部已会回退到 javacap
- **节省**: ~3s/次

#### 优化 2: Allure 报告异步生成
- **文件**: `app/app_automation/executors/test_executor.py` + `app/app_automation/tasks.py`
- **变更**: `run_tests()` 中不再同步调用 `_generate_allure_report()`，改为通过 Celery 异步任务 `generate_allure_report_async.delay(execution_id)` 后台生成

- **节省**: ~12s/次
- **注意**: 需要重启 Celery worker 使新任务生效 (worker 需重新加载模块以识别 `generate_allure_report_async`)

### 第八轮：Allure 报告静态资源 404 修复（Nginx location 优先级）

用户反馈报告页面 CSS/JS 全部返回 404，`index.html` 返回 200。

**真正根因：** Nginx `location ~* \.(js|css|png|...)` 正则规则的优先级高于普通前缀 `location /app-automation-reports/`。请求 `styles.css` 时先匹配正则规则，从 `frontend/dist/` 查找文件（不存在→404）。

**修复方案：** 将 `location /app-automation-reports/` 改为 `location ^~ /app-automation-reports/`，`^~` 前缀提升优先级使其高于正则 location。

**修改的文件：**
- `C:\nginx\conf\nginx.conf`（实际运行的配置）— `location /app-automation-reports/` → `location ^~ /app-automation-reports/`
- `C:\nginx\conf\nginx.conf` — `location /app-automation-templates/` → `location ^~ /app-automation-templates/`（同样的问题，预防性修复）
- `frontend/nginx.conf`（项目内的参考配置）— 同样修改

**Nginx location 优先级（从高到低）：**
1. `location = /exact` — 精确匹配
2. `location ^~ /prefix/` — 优先前缀匹配
3. `location ~* \.regex$` — 正则匹配
4. `location /prefix/` — 普通前缀匹配

**验证：** 所有 CSS/JS/plugin 资源均返回 200，`nginx -s reload` 成功。
